# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Personal portfolio site for Ayush Srivastava built on Next.js 16 (App Router) with Payload CMS 3 for content management and a Gemini-powered chatbot. Payload's database adapter points at a Supabase-hosted Postgres instance, and there's also a separate `integrations/supabase` client used elsewhere in the app — this repo mixes two different "backends" (Payload/Postgres for CMS content, Supabase client for other integrations).

## Commands

**Use `pnpm`, not `npm` or `npx`, for everything in this repo.** `pnpm-lock.yaml` is the authoritative lockfile; `package-lock.json` and `bun.lockb` are stale leftovers from earlier tooling experiments. Running `npm install` here has repeatedly produced `ERESOLVE` conflicts and duplicate nested package instances that `npm` can't untangle — `pnpm install` resolves cleanly every time.

```bash
pnpm dev             # start Next.js dev server (localhost:3000, admin at /admin)
pnpm build           # production build
pnpm start           # start production server
pnpm lint            # next lint
pnpm payload         # run the Payload CLI (e.g. pnpm payload generate:importmap) — see caveat below, currently broken
pnpm seed            # seed the database via src/seed/seed.ts (uses ts-node/esm loader)
```

There is no configured test runner in package.json — check with the user before assuming a test framework/command.

### Payload CLI is broken on this machine's Node version

`payload generate:importmap`, `payload migrate:create`, etc. all fail with `ERR_REQUIRE_ASYNC_MODULE` / `ERR_REQUIRE_CYCLE_MODULE` on Node 24 — the CLI's `tsx`-based config loader can't `require()` this project's ESM `payload.config.ts`. Payload 3.x officially targets Node 18/20/22; Node 24 is ahead of that.

**Workaround that works:** write a throwaway `.mjs` script that dynamically `import()`s both `payload` and `payload.config.ts` (never `require()`), load `.env.local` manually via `dotenv.config({ path: '.env.local' })` (a standalone script doesn't get Next's automatic env loading), then run it with `node --experimental-strip-types your-script.mjs`. This has been used successfully to regenerate `app/(payload)/admin/importMap.js` by calling `generateImportMap()` from `payload/dist/bin/generateImportMap/index.js` directly. Delete the scratch script after use — don't commit it.

In practice this workaround is rarely needed: `pnpm dev` regenerates the import map itself at startup (see Postgres push section below) — reach for the manual script only if you suspect the map is stale and a dev-server restart alone hasn't fixed it.

## Architecture

### Two route trees for Payload

Payload's Next.js integration generates routes under `app/(payload)/`:
- `app/(payload)/admin/[[...segments]]/page.tsx` — the Payload admin UI
- `app/(payload)/api/[...slug]/route.ts` — Payload's REST API catch-all (**generated file, do not hand-edit** — it's regenerated by Payload)
- `app/(payload)/api/graphql/route.ts` — Payload GraphQL endpoint
- `app/(payload)/api/portfolio/route.ts` and `app/(payload)/api/chatbot/route.ts` — custom, hand-written API routes alongside the generated ones

The frontend lives in its own route group, `app/(frontend)/`, matching Payload's documented convention of keeping generated `(payload)` routes and hand-written app routes separate (`layout.tsx`, `page.tsx`, `not-found.tsx`, `globals.css`, `providers/` all live there now — not loose at `app/` root).

### Payload version coupling — bump `@payloadcms/*`, `payload`, and `next` together

`@payloadcms/next` declares a peer-dependency range on `next` (e.g. 3.86.0 requires `next@>=16.2.6 <17`). Bumping only the `@payloadcms/*` packages without also bumping `next` to satisfy that range leaves `pnpm install` reporting an unmet peer, and in the worst case leaves two separate resolved copies of `@payloadcms/ui` installed side-by-side in `node_modules/.pnpm` (a phantom-duplicate situation `pnpm dedupe` does **not** reliably fix — a full `rm -rf node_modules pnpm-lock.yaml && pnpm install` was what actually resolved it last time). Always bump `payload`, every `@payloadcms/*` package, and `next` in the same commit, then do a clean reinstall and verify `find node_modules/.pnpm -maxdepth 1 -name "@payloadcms+ui@*"` returns exactly one directory.

### The two auto-generated `(payload)` route files must pass the real import map, not a config stub

`app/(payload)/layout.tsx` and `app/(payload)/admin/[[...segments]]/page.tsx` are Payload-generated files that call `RootLayout(...)` / `RootPage(...)` respectively. Both take an `importMap` argument that must be **the actual generated map object** — `import { importMap } from './admin/importMap.js'` (or `'../importMap.js'` from the nested route) — not `{ baseDir: process.cwd() }`. That `baseDir` shape is a config hint used only when *generating* the map, not the map itself; passing it to `RootLayout`/`RootPage` silently breaks every default-registered admin widget (symptom: the `/admin` dashboard renders completely blank with a console error `getFromImportMap: PayloadComponent not found in importMap`, even though `importMap.js` on disk looks correct) while every other admin route (collection lists, document edit views) keeps working fine, because those don't depend on the widget system. If you ever see this exact blank-dashboard symptom, check these two files first before assuming the generated map itself is stale.

### Postgres schema `push` can block on an interactive prompt in dev

`payload.config.ts`'s `postgresAdapter` sets `push: process.env.NODE_ENV !== 'production'`, so schema changes in `payload.config.ts` (new fields, renamed fields) sync to the dev database automatically on next `pnpm dev` start — no manual migration needed in development. But if a field is **renamed or removed** in the same collection where a field is **added**, Drizzle's push tool can't tell an addition-plus-removal from a rename and drops into an interactive terminal prompt ("Is X column created or renamed from Y?") that a backgrounded/non-TTY dev server process will hang on indefinitely (requests just time out, no error). If a schema change involves both an addition and a removal in the same collection, either do them as two separate `pnpm dev` restarts (add first, confirm it pushes cleanly, then remove in a follow-up restart) or accept the field rename ambiguity by choosing distinctly-named new fields so Drizzle doesn't see a plausible rename pair.

### Payload config and schema

`payload.config.ts` is the single source of truth for CMS collections and globals: `users`, `hero-content`, `experiences`, `projects`, `skills`, `contact-info`, `uploads`, `chat-messages`, plus a `site-settings` global. Access control is public-`read`/authenticated-`create,update,delete` on content collections; `users` and `chat-messages` are fully locked to authenticated requests only (`chat-messages` is written server-side via the Local API with an anonymous `visitorSessionId`, not by public clients).

`projects` has `versions: { drafts: true }` and an `admin.preview` function — draft case studies can be edited and previewed before publishing. The `@payloadcms/plugin-seo` plugin is wired for `projects` and `site-settings`, adding a `meta: { title, description, image }` field group to each.

Payload generates `payload-types.ts` (TypeScript types for all collections/globals) from this config — regenerate via the Payload CLI (see caveat above; use the manual `.mjs` workaround on this machine) after changing `payload.config.ts` rather than hand-editing the generated file.

The Postgres connection string is read from `process.env.DATABASE_URL` (set in `.env.local`, gitignored) — never hardcode it back into `payload.config.ts`. If the password contains special characters (e.g. `$`), it must be URL-encoded (`$` → `%24`) inside the connection string or `pg` throws a cryptic `SASL: SCRAM-SERVER-FIRST-MESSAGE: client password must be a string` error that has nothing obviously to do with URL-encoding.

### Chatbot

`app/(payload)/api/chatbot/route.ts` is a streaming POST endpoint backed by `lib/chatbot/ChatbotService`, which wraps `@google/generative-ai` (Gemini) and requires `GEMINI_API_KEY` to be set — the route throws at module load time if it's missing. `ChatbotService` fetches portfolio context via `lib/payload/getPortfolioData()` (the same shared helper used by the homepage and `/api/portfolio`) — it does **not** self-fetch its own HTTP API. The frontend widget lives in `components/Chatbot/ChatbotWidget.tsx` and is mounted once, in `app/(frontend)/layout.tsx` — don't add a second instance elsewhere.

### Content flow

`app/(frontend)/page.tsx` is a Server Component that calls `lib/payload/getPortfolioData()` once, using Payload's Local API directly (no HTTP round-trip), and passes the resolved data down as props to `Hero`, `Experience`, `Projects`, `Skills`, `Contact` (each still `'use client'` for interactivity, but no longer self-fetching). `app/(payload)/api/portfolio/route.ts` wraps the same helper for anything that needs a public JSON endpoint. There is no more client-side fetch waterfall or loading-skeleton flash on first paint — if you're tempted to add a `useEffect` fetch back into a section component, don't; extend `getPortfolioData()` instead and thread the new field through as a prop.

### Supabase

`integrations/supabase/{client.ts,types.ts}` provides a separate Supabase JS client, and `supabase/` at the repo root holds Supabase-specific config/migrations (`supabase/config.toml`, `supabase/migrations`). This is distinct from the Payload/Postgres migrations under `src/migrations`. Don't assume the two migration directories are related — confirm which system a given migration belongs to before modifying.

### UI stack

Uses shadcn/ui conventions (`components.json`, Radix UI primitives under `components/ui/`), Tailwind CSS v4 (`@tailwindcss/postcss`, `tailwind.config.js`), `next-themes` for dark mode, and `framer-motion` for animation. Path alias `@/*` maps to the repo root (see `tsconfig.json`).

### TypeScript config notes

`tsconfig.json` has `strict: true` but individually disables `noImplicitAny`, `noUnusedParameters`, `noUnusedLocals`, and `strictNullChecks` — effectively a loose strict mode. Don't tighten these without checking whether existing code relies on the relaxed behavior.
